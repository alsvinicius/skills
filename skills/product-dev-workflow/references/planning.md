# MVP-first planning

Read [the template](../assets/templates/implementation-plan.md). Inspect all prerequisite contents, source revisions, and unresolved decisions.

Choose the smallest set of complete journeys delivering useful value to intended users and validating the core product. Include essential security, integrity, deployment, recovery, and documentation. Include observability and performance only when a confirmed need or evidence makes them material, following [observability and performance](observability-and-performance.md). Infrastructure alone or unfinished feature fragments are not a delivered MVP. Record included REQ/JRN IDs, exclusions, deferral rationale, release criteria, and usefulness measures. Honor confirmed business constraints and explain scope tradeoffs.

Make Phase 1 the MVP delivery phase, and inside it mark the **minimum testable slice**: the smallest set of tasks without which the core hypothesis cannot be tested by real users. Flag every other Phase 1 task as outside that slice so `/mvp` defers it. Record how the slice will be tested. Choose later phases by value and dependencies; phase count is unrestricted and a scale phase is optional. Give each phase complementary delivered value and exit criteria. Account for every requirement through a phase, explicit deferral, or retirement.

Every TASK includes title, bounded description, source IDs, dependencies, useful subtasks, Definition of Ready, Definition of Done, measurable expected results, and affected documentation. Write tasks so a coding agent can execute them autonomously inside the approved product scope: identify authoritative inputs; state constraints and permitted implementation choices; name observable outputs and evidence; link BDD scenario IDs to automate; give validation commands when known or a project-grounded discovery rule when unknown; and define when to stop and report a blocker. Do not leave routine implementation decisions as vague “decide during implementation” notes. Give the agent selection criteria and authority to make reversible choices, while routing product, scope, security, compatibility, cost, and irreversible choices to the user. DoR identifies required inputs/decisions. DoD identifies completion evidence, appropriate verification, affected documentation, and deployment when applicable. Avoid arbitrary coverage targets and generic checklists.

Plan security validation proportionately, following [product security](security.md): authorisation BDD scenarios for security requirements, existing or chosen automated checks, and vulnerability or penetration testing only when justified, authorised, and run inside the harness. Do not make penetration testing mandatory.

When cost is requested or material, follow [project costs](project-costs.md): link cost tasks to their `REQ` and `COST` IDs, add decision points before paid services, recurring commitments, and deployment, and name the evidence (price source and date, usage basis, approval) in the DoD. Add a paid-spend gate to any task that could create a paid account or commit spend; do not plan purchases or billed trials.

Plan observability and performance validation only for confirmed or material needs, following [observability and performance](observability-and-performance.md): link each applicable TASK to its REQ and BDD IDs, use the real commands in `docs/harness/validation.md`, and record unknown targets as open questions rather than planning around invented numbers. Do not plan unrequested or production load tests.

## Task admission for existing products

For a brownfield product, a TASK must trace to work that does not yet exist in the repository. Admit a task only when it is one of:

1. **Change:** a confirmed change to an existing capability (`change` mode), with its `REQ` IDs and BDD scenarios.
2. **Confirmed pending work:** unfinished work the user has confirmed from versioned documentation, issues, or a roadmap. A TODO, a commented-out feature, or a stale statement in docs is not enough on its own; cite the confirmation.
3. **Documentation maintenance:** creating or correcting Diátaxis docs, `AGENTS.md`, or product artifacts that are missing or stale for the actual product.
4. **Migration or compatibility:** only when the confirmed scope requires it.

Existing behaviour that the user confirms as current is not a task. Record it as `as-built` in the assessment, PRD, or journeys, with its evidence IDs, and list it in the full scope coverage table as `as-built (no task)`.

In `as-is` mode with no admitted tasks, the plan's MVP outcome section states that no MVP is needed, its Phases section lists no phase, and it states "no implementation tasks: as-is documentation". It does not suggest the harness, `/mvp`, or `/execute`. In `as-is` mode with only documentation tasks, the plan admits those tasks and recommends executing them, not building an MVP.

Order dependencies without cycles. Split oversized tasks. Keep blocked work visible and draft. Estimate effort/dates only with explicit capacity assumptions; do not assert unsupported commitments. Include maintenance of the four mandatory files at actual/planned project boundaries and applicable Diátaxis docs in tasks and DoD. For `AGENTS.md`, require the concise product-workflow guidance described in [shared documentation rules](documentation-and-repo-rules.md); update it only when its paths, boundaries, commands, or durable instructions change.

Completion: Phase 1 delivers a complete useful outcome; full scope is accounted for; every task has required fields and is actionable by a coding agent without an implicit user decision; dependencies are coherent; each task names applicable BDD IDs and required validation evidence; no thread remains open without an explicit user-authorized TBD disposition; blockers, exact source revisions, workflow state, and documentation navigation are current. Include ADR creation for technical decisions and an index update in the relevant task DoD, and note prototype and harness suggestions when they apply (see [prototypes](prototypes.md) and [harness and agents](harness-and-agents.md)). Once the plan is ready and admits implementation tasks, suggest the harness (needs approval), then recommend `/mvp` for the minimum testable slice or `/execute` for the full project. For an `as-is` plan with no admitted tasks, skip these suggestions and report that no implementation is needed. Do not begin implementation as part of planning unless the user also requested it.
