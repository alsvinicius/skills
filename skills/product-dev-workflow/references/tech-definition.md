# Technical definition

Read [the template](../assets/templates/technical-definition.md), the PRD, journeys, and [domain model](domain-model.md), and deferred technical preferences.

Interview about existing systems, preferred languages, team skills/capacity, development workflow, testing, hosting/cloud, budget, integrations, data sensitivity, reliability, performance, accessibility, compliance, and operations. Mark unknowns. Verify material current tool capabilities in authoritative documentation when necessary. When cost is requested or material, build the cost model per [project costs](project-costs.md) ([template](../assets/templates/cost-model.md)) and link it from the technical definition rather than repeating its lines; the budget answer feeds it.

Define implementation for full scope, separating MVP needs from future extension points. Start from the bounded contexts and context map; justify any deviation in an ADR, and confirm or revise the candidate aggregates. Generate architecture and sequence diagrams per [diagrams](diagrams.md). Choose the simplest architecture meeting confirmed requirements; example technology lists are not defaults. Document components/boundaries, data ownership/lifecycle, contracts, integrations, access rules, failure handling, security, quality targets that are confirmed or agreed, development setup, testing strategy, CI/CD, deployment, recovery, and observability or performance design when a confirmed need makes them material ([observability and performance](observability-and-performance.md)). Scale detail to requirements and explain relevant omissions.

Ask whether to adopt test-first development (TDD) and record the answer per [test-first development](tdd.md); do not assume it.

Define a code style baseline per language and subproject following [code style](code-style.md) ([template](../assets/templates/code-style.md)): tooling taken from existing configs or recommended, enforceable rules as `STY` IDs, and the commands the harness will use. Link it from the technical definition rather than repeating it.

Choose the deterministic enforcement strategy per [deterministic enforcement](deterministic-enforcement.md): which checks, validators, and git hooks the project needs, the single entry point, and whether CI exists. Record it in the ADR with the code style baseline, and do not create the scripts or hooks yet.

Create one [ADR](adr.md) file per technical or architectural decision in `docs/adr/` with an index; each DEC in the technical definition is a short summary linking to its ADR, which holds status, alternatives, rationale, consequences, evidence, and REQ/JRN IDs. If the product has a frontend, suggest prototypes and ask for approval ([prototypes](prototypes.md)). Distinguish recommendations from user preferences. Surface feasibility conflicts for business decisions.

Completion: full scope has implementation coverage or explicit disposition; material constraints, decisions, contracts, and operations are documented; MVP and future scope are distinguished; every thread is decided, retired, or explicitly deferred by the user before `ready`; actual/proposed subprojects and mandatory files are identified under shared rules; the testing approach (test-first, tests-with-code, or the user's explicit deferral) is recorded; a code style baseline exists for each language and subproject in scope, or its absence is explicitly deferred by the user.
